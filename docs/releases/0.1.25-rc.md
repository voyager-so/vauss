Vauss 0.1.25-rc adds 360 equirectangular input.

- **360 footage and photos.** `vauss run` now detects 2:1 equirectangular input automatically (or take it explicitly with `--camera-model equirect`). Each 360 frame is split into 14 overlapping pinhole views (12 around the horizon plus straight up and straight down), the 14 views are solved as one rig in COLMAP so they share a single pose per frame, and the existing trainer, viewer, web, Blender and game exports all work unchanged. If ordinary 2:1 video is misdetected, add `--camera-model pinhole`.
- **Operator and tripod masking.** The area straight down, where the camera operator or tripod sits in every frame, is masked out of training; adjust with `--nadir-mask-deg` (default 30, 0–60).
- **Honest scoring.** Held-out evaluation holds out whole panoramas, never single views of a panorama that also trains, so scores aren't inflated by overlapping pixels. `--target-count` counts 360 frames (100 by default, 20–250).
- **Results on OmniPhotos (CC BY 4.0, real Insta360 captures).** Temple3: 72/72 panoramas solved in one model, held-out PSNR 25.5 dB, LPIPS 0.107. Ballintoy: 94/94 panoramas, 31.1 dB, LPIPS 0.165. Without the rig, the same Temple3 frames placed only 43% of views in eight disconnected pieces.

Known limitations: camera solving for 360 is slow, 31–40 minutes for 72–94 frames on a 32-core machine, mostly feature matching; a speed-up is tracked. 360 runs need the default backend and don't support `--trust-poses` or a quick preview. Input must be stitched equirectangular; raw dual-fisheye files (for example Insta360 .insv) are not read yet.
