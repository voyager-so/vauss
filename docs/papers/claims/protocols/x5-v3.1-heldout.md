## The cap rule (fixed before any probe result; text bound in the probe's job.json)

```
cap(W, H, n_images, n_test) = min(11.0e6, floor_to_0.5e6( (14.5 − A − G − c · MP_train) / β ))
MP_train = (n_images − n_test) · W · H / 1e6        # training views preloaded on the GPU (PRELOADING_LEVEL 2)
c        = 12 B/px = 0.011176 GiB per training MP    # float32 RGB; fixed by the data layout, not fitted
```

- **A, β:** least squares of (peak at 12k − c·MP_train) = A + β·cap over the m60 probe arms that exit 0 (caps 5M / 7.5M / 9.5M, 12k steps, seed 92). The fit is done separately on the setup-subtracted NVML increment and on the torch whole-process peak. The rule takes whichever measure gives the smaller cap.
- **G (late growth; amendment 08:16, before any result):** m60 at 7.5M run to the full 30k steps, including the 5k PPISP controller (seed 93). G = its 30k peak − the 12k peak at 7.5M, floored at 0, per measure.
- **Why m60's slope for every scene:** m60 is the scene with known excess memory per splat. All 9 M360 scenes fit at 11M in v2, while m60 OOM'd. A single conservative slope is the cost of one rule: **family and horse may get a cap below 11M because of m60's slope.**
- **G fallback (sub-lead 08:18, declared before any result):** if the 30k companion has not landed by 09:05 PT, G = 1.5 GiB for both measures. The 30k result is then descriptive only.
- **Failure handling:**
  - If fewer than 2 of the 12k arms exit 0: cap = the largest 12k cap that exits 0 with both peaks ≤ 14.5 GiB.
  - If the 30k companion OOMs: the largest 12k cap whose predicted 30k peak is ≤ 14.5 GiB.
  - If nothing fits: stop and report.
- **Not resolution-only:** m60's views (0.55 MP) are smaller than M360's (1.0–1.6 MP), and its training-image load (~151 MP) matches M360 outdoor. So the excess is scene geometry (rasterizer tile intersections), not pixel count. The resolution term enters only through MP_train.

## Disclosures

- STACK's cap differs from v3 (and from the M360 claim groups, which keep 11M; this registration changes nothing on M360).
- The rule's constants come from m60, a verdict scene. That is a memory-only, score-blind measurement on separate seeds (92/93), never a quality read. It is disclosed as "the cap was fitted on m60's memory".
- NHT keeps its upstream 2.5M T&T cap. Neither arm's cap is matched to the other ("both at their recipes").
- If a capped STACK still OOMs, the pair is reported as failed. There are no reruns and no further cap changes inside v3.1.
